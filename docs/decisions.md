# Active Decisions

Updated 2026-10-14. This file contains only decisions that govern the current product.

## Product and validation

1. **Product:** Build an agent-first personal trip assistant centered on a living Trip Workspace. Unknown place, activity, date, time, budget, or travel mode may remain open while the agent discovers and compares options.
2. **First release and phase order:** Validate a same-day local-outing journey on mobile web (Phase 0). Trip history (Phase 1), confirmed patterns and routines (Phase 2) and routine reminder notifications through web push (Phase 3) follow on web, before Android. Android, Calendar, multi-stop and multi-day work stay gated as in [trip-assistant-roadmap.md](trip-assistant-roadmap.md). Android work begins only after the pilot demonstrates useful proposals, action, repeat use, quality, and sustainable cost.
3. **Planning method:** The language model interprets goals, proposes questions, compares grounded options, and explains plans. Typed tools provide places, routes, weather, Calendar context, memory, reminders, and actions. Ordinary Places and Routes API payloads are rendered by the server and are not placed in model context (see decision 17). Deterministic solvers are optional tools for constrained schedules rather than the product's central planner.
4. **Question policy:** Ask the next question only when its answer can materially change feasibility, ranking, safety, permission, or an external action. Present grounded options early and keep assumptions visible and editable.

## Access and cost

5. **Anonymous first use:** Start with a silent anonymous identity and no login screen. A guest receives 50 successful user turns or 10 activated trips, whichever comes first. A registered free account receives 100 successful turns and 10 activated trips per rolling 30 days. Limits are versioned pilot hypotheses.
6. **Model hosting:** Use a provider-neutral server gateway with a low-cost open model reached through OpenRouter as the default and at most one bounded stronger-model escalation. Every request pins the provider and requires zero data retention and no training use. Gemini is not used in the first version. Do not self-host during pre-seed validation. After a live bake-off on 2026-10-17 the owner approved `google/gemma-4-31b-it` at DeepInfra as the primary FRAME model and `qwen/qwen3-next-80b-a3b-instruct` at DeepInfra as the second. Both stay behind the gateway's pinned-provider and zero-retention rules, and written DeepInfra terms are still required before pilot traffic. Details and results are in [model-hosting-decision.md](model-hosting-decision.md).
7. **Deployment:** Use a scale-to-zero managed backend with strict user, workspace, daily, and pilot-wide quotas. Provider credentials remain server-side.

## Scope and safety

8. **Travel-only boundary:** Serve trip and outing discovery, planning, execution, and recovery plus app help. A server-owned gate classifies requests before the planning model. Out-of-scope requests receive a fixed redirect with no search, route, or general-answer tool call.
9. **Tool authority:** The server owns tool allowlists, permissions, state transitions, evidence freshness, and external-action approval. Model output is an untrusted proposal until schema, policy, evidence, and budget validation succeeds.
10. **Token ceilings:** Limit user input to 2,000 tokens; each planning call to 12,000 compiled input and 1,200 output tokens; and each run to 40,000 input, 4,000 output, six model calls, twelve tool calls, and one escalation. Truncated, malformed, or over-budget output cannot update state or trigger an action.
11. **Voice activation:** Android starts with an in-app press-and-hold microphone button. Release submits, Cancel discards, capture stops after 60 seconds, and raw audio is discarded after transcription. The microphone is otherwise off.
12. **User control:** Calendar, location, trip history, pattern suggestions, notifications, and monitoring are requested in context, each with its own consent, and remain optional. Persistent memories, history and assumptions are visible, editable, and deletable. External writes require a preview and explicit confirmation.

## Quality gates

13. **Grounding:** Material claims about places, hours, routes, travel time, weather, availability, or disruptions require fresh provider evidence and provenance. Google Maps grounded output is shown verbatim with its sources and counts as that evidence.
14. **Evaluation:** Do not expand beyond the validation release until offline boundary, safety, grounding, token, identity, and cost gates pass and at least 30 supported real goals demonstrate repeat value. Google Maps content and grounded output may not be used to test or validate AI systems, so offline fixtures use synthetic place data; live traffic is measured only on structural checks.
15. **No precision promise:** Recommendations communicate evidence, freshness, uncertainty, and alternatives. The product does not promise exact or guaranteed arrival times.

## Data, history and proactive features

16. **Discovery path:** Open-ended discovery uses Google Maps Grounding Lite through a server-side MCP client with the OpenRouter model. The grounded output is displayed unmodified with its Google Maps sources immediately after it. The server may add framing above it but cannot edit, trim, reorder or intersperse it. Grounding Lite is reported as Generally Available (announced 22 April 2026) with a 99.9% uptime objective and no Canadian exclusion, per the owner-supplied analysis; confirming this for the owner's own billing account is still tracked as a legal gate in [docs/legal/open-questions.md](legal/open-questions.md).
17. **Places and Routes payloads:** Until a written Google determination says otherwise, ordinary Places and Routes API payloads are fetched and rendered by the server and are not placed in LLM context, text-to-speech or durable history. The model sees only opaque place IDs and the user's own data for these. Evidence carries an `llm_visible` flag so this can change without a redesign. The owner asked whether user consent could allow it. User consent addresses privacy, not Google's licence. The analysis the owner supplied on 2026-10-15 ([legal/google-maps-grounding-lite-qa-2026-10-15.md](legal/google-maps-grounding-lite-qa-2026-10-15.md)) says the ordinary Places API pipeline cannot be approved under the published terms and offers no safe-field list, so the rule stands. Grounding Lite is the permitted way for the model to read place data. Only a written Google determination changes this.
18. **Maps content storage:** Store only place IDs (indefinitely) and user data. Grounded output may be cached only for redisplay with a hard maximum of 30 consecutive days (default 24 hours). Names, addresses, hours, ratings, categories and reviews are re-fetched by place ID at display time and are not stored. Coordinates returned by Grounding Lite are not cached at all, because no equivalent allowance is documented; coordinates from the Places API may be cached at most 30 days. The 30-day allowance for grounded output covers redisplay and display evaluation, not a "recent answers" history, so the history screen is built from place IDs and user data. A `save_to_maps_url` is shown as returned and is not stored until Google clarifies. Patterns are not grouped by place ID until Google confirms that use (decision 20).
19. **History:** A per-user outing history stores only user actions and user-supplied data (place ID, the user's label, an activity tag derived from the user's own request, timestamp, outcome and feedback). It is opt-in, with a 180-day rolling retention ceiling that the user can shorten or switch off but not extend for now (owner decision, 2026-10-15), and the notice states the period. Guests keep it on the device; registered users may store it on the server. See [data-and-history-design.md](data-and-history-design.md).
20. **Patterns and routines:** From Phase 2, patterns are computed deterministically from stored history. A pattern is shown to the user with its basis and becomes a routine only through a confirmed `PendingAction`. Nothing inferred is stored or treated as a hard fact without the user's confirmation.
21. **Routine reminder notifications:** From Phase 3, a registered user who has confirmed a routine and separately opted in may receive a web-push reminder at the routine's time. The text is generic and names no place. There is no model call, no Maps content and no background location in the trigger path. Guests receive none.
22. **Legal gates:** Legal and privacy questions that gate a phase are tracked in [docs/legal/open-questions.md](legal/open-questions.md) and in GitHub issues. The legal summary supplied by the owner on 2026-10-13 is stored in [docs/legal/google-maps-llm-policy-summary.md](legal/google-maps-llm-policy-summary.md). Neither is legal advice or a determination from Google. On 2026-10-17 the owner instructed that the lawyer's summary be treated as the final Google answer and that the open Google questions not be sent; the choices the summary does not cover stay conservative and are recorded as accepted risks in [legal/open-questions.md](legal/open-questions.md).
23. **Phase 0 model boundary:** The model never sees Google Maps content in Phase 0. A single FRAME call turns the user's message and user-derived workspace facts into a validated workspace patch, an intent and typed search arguments, with no tools and no reply text. The server runs the Grounding Lite search under a per-run budget, validates the result against the tool-call ledger and shows Google's output verbatim in a typed `discovery` block; all reply text is server-authored. Trade-off: the assistant cannot discuss or compare specific places or answer follow-ups about them. A `maps_content_to_model` runtime flag, default off and unimplemented, is the switch for a later phase and stays off until Google confirms in writing that the model provider's handling is acceptable. The model's FRAME output is a minimal proposal (an intent, an optional search and optional soft facts); the server builds the workspace patch, status and next action itself, ignores a search attached to an OTHER intent, and degrades a missing or rejected query to a fixed clarification instead of failing a paid call. A turn that ends in that fixed clarification (intent OTHER, or a discovery proposal whose query was rejected) does not consume the user's allowance (owner decision, 2026-10-17); its cost is still recorded and counts toward the daily ceiling, and a per-user limit on such free turns applies. A search with no usable area carries a fixed default location bias, a circle of 40 km around downtown Toronto (43.6532, -79.3832), because a live run showed that without one Google returned results from Quebec; a search with a named area carries no bias. These are public constants for the Phase 0 Toronto/GTA scope, never derived from the user, the message, the client or the model, and the model cannot supply a bias. The user's own location (foreground location with consent) is a later phase. Model-proposed facts are unconfirmed soft inferences and never override user or server facts. Internal cost ceilings are enforced before the model call: a rolling 24-hour token ceiling from the entitlement policy and a limit on paid failed turns per hour (owner-tunable, default 10), because failed turns refund the user allowance but not the cost. Every cost entry is attributed to the user or to the provider side. Provider-side failures (timeouts, 5xx, provider rate limits, kill switch, deadline partials) are recorded at worst-case charge but do not count toward the user's own daily ceiling (owner decision, 2026-10-16); successful turns and abuse-shaped failures do. A whole-pilot spend budget over the provider-attributed total is required before pilot traffic (ACCESS-02).
